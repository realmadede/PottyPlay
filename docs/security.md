# PottyPlay Security and Privacy Controls

This document describes implemented controls and intended safeguards; it is not a security certification. The current mobile validation used an emulator-only debug configuration. That mode permits local HTTP traffic and disables the Privacy Screen plugin for inspection. It must not be used for distribution. Production-origin, physical-device, and store-release verification remain outstanding; see [the mobile guide](mobile.md).

## 1. Threat Model & Mitigations

| Threat | Attack Vector | Mitigation in PottyPlay |
| --- | --- | --- |
| Ticket Reuse / Multi-streaming | Multiple users sharing one ticket number | Database transactions + unique constraint on `ticketId` ensure only one active session per ticket. |
| OTP Brute-Forcing | Automated submission of 6-digit codes | Maximum 3 attempts enforced per challenge; challenge locks after 3 failures. |
| SMS Flooding / Cost Exhaustion | Automated scripts repeatedly requesting OTPs | IP and phone rate limits (max 5 requests per 10 minutes per phone). |
| Session Hijacking | Guessing session tokens | Cryptographically secure 256-bit random tokens (`crypto.randomBytes(32)`). |
| Time Tampering | Patron changing device clock to extend break | Authoritative backend clock; `expires_at` is evaluated on the server, not the client. |
| Cross-Tenant Exposure | Operator accessing screenings or tickets of another cinema | Tenant scoping ensures tickets and screenings belong to authorized venue IDs. |
| Credential Leakage | API keys or OTP codes in logs or frontend bundles | Africa's Talking API key restricted to server-side adapters; raw OTPs hashed with SHA-256. |
| Theatrical Leakage | Unauthorized long-term recording or restreaming | 15-minute hard stop, immediate operator revocation, and synchronized fail-closed playback. |

## 2. Cryptographic Controls

- **OTP Hashing:** OTP codes are transformed with `crypto.createHash("sha256")` alongside application salts before storage. Plaintext OTPs never touch the database.
- **Timing Attack Prevention:** OTP hash verification uses a constant-time comparison loop to prevent character-by-character timing leaks.
- **Session Tokens:** Tokens use a `pstk_` prefix followed by 64 hexadecimal characters of entropy generated by Node's system CSPRNG (`crypto.randomBytes(32)`).

## 3. Server-Authoritative Access Control

- All playback synchronization endpoints (`/api/sessions/sync`) require the session token.
- Access is denied when:
  - Session status is `EXPIRED`, `REVOKED`, or `FAILED`.
  - The current server timestamp exceeds `expiresAt`.
  - The screening has concluded or is cancelled.
  - The cinema venue lacks active studio rights authorization for the content asset.

## 4. Screen-Capture Risk Reduction

PottyPlay uses technical controls intended to reduce casual screen capture. No app can guarantee prevention of external-camera recording, modified operating systems, or all capture methods; these controls do not replace content licensing and operational safeguards:

### 4.1 Native Mobile Protections (`@capacitor-community/privacy-screen`)
- **Android `FLAG_SECURE`**: Enabled in the normal/release configuration to block standard Android screenshots and blank many OS screen recordings. Emulator-only debug mode disables this protection so test screens can be inspected.
- **iOS App Switcher Blanking**: Configured to obscure sensitive app content when the app is backgrounded; iOS behavior still requires device testing.

### 4.2 Web Companion Best-Effort Controls (`CinemaCanvasPlayer.tsx`)
- **Dynamic Floating Watermark**: Renders a drifting forensic watermark across the canvas continuously displaying:
  `LICENSED PATRON: [phone/ID] • SESSION ID: [ID] • TC: [timecode]`. The watermark may help investigate a retained recording if its text is legible; it cannot guarantee attribution.
- **Capture-Shortcut Handling**: Attempts to intercept selected keyboard shortcuts; browser and operating-system capture tools may bypass page-level handlers.
- **Focus Loss Stream Blanking**: Uses `window.blur` and `document.visibilitychange` as best-effort signals to blank the player when the page loses focus.
- **Clipboard Clearing**: Attempts to clear clipboard content on selected key events where browser permissions permit.
- **Context Menu & Selection Disabled**: Browser right-click inspection and text dragging are suppressed (`onContextMenu` blocked, `user-select: none`).

## 5. Mandatory Patron Identity Registration Gate (`/watch`)

To satisfy studio exhibition requirements, anonymous viewing of companion break streams is strictly forbidden:
- Patrons scanning a seat QR code or entering a ticket barcode must register and verify their telephone number via Africa's Talking SMS OTP prior to receiving an active session token.
- Unregistered patrons are blocked by an authentication modal barrier; streams cannot be initiated anonymously.

## 6. Partner Application Security & Bot Honeypot Defenses

The public cinema partnership application endpoint (`/api/partner/register`):
- **Honeypot Trap**: Employs a hidden form field (`website_url_hp`) that is invisible to human operators. Automated scrapers filling this field are silently rejected with status 400.
- **Origin Telemetry**: Records client IP address (`ipAddress`) and HTTP user-agent (`userAgent`) on `PartnerApplication` records to verify venue geographic origin and detect bot farms.

## 7. Expiring One-Time Registration Invitation Workflow

Cinema venue registration is restricted to invite-only administration:
- **Expiring Links**: Registration invitation links dispatched to verified circuits expire after 48 hours or immediately upon receipt of credentials in the database (single-use token enforcement).
- **No Public Self-Registration**: The operator portal (`/operator`) provides strictly sign-in and password recovery flows; all cinema tenant provisioning is governed through platform administration (`/x`).

## 8. Operator and Console API Access Control

All operator-facing endpoints (`/api/operator/tickets`, `/api/operator/screenings`, `/api/operator/dashboard`, `/api/operator/revoke`, `/api/operator/pricing`, `/api/simulator/playback`) pass through the shared guard in `src/lib/auth-guards.ts`:

- **Authentication**: a bearer token (or the `pp_operator_token` cookie) is required. A platform administrator token (`adm_...`) is accepted only when its HMAC signature, expiry and active database record are all valid; the prefix alone grants nothing.
- **Tenant isolation**: an operator is always bound to the cinema stored on its session. Supplying a different cinema through the query string, the `x-cinema-id` header or the request body returns 403. Revoking or controlling a resource of another cinema is indistinguishable from it not existing (404).
- **Roles**: pricing changes require the `MANAGER` or `ADMIN` operator role (or a platform administrator). Projectionists can control playback but not pricing.
- **Privacy**: viewer phone numbers returned to the projection console are masked.
- **Simulation actions** (`simulate_delay`, `simulate_sync_failure`) are rejected in production unless `ENABLE_SIMULATOR=true`.
- **`/api/screenings/current`** has no anonymous access and no default screening: patrons receive only the screening of their own active session; operators receive screenings of their own cinema.
- The projection console (`/cinema`) sends the operator token stored by the operator sign-in; without a session it shows a sign-in notice.

### 8.1 Content rights are granted by platform administration only

Operators cannot create content assets or grant themselves rights. Scheduling a screening requires an existing, authorized `RightsAuthorization` for that cinema that covers the scheduled start time. Rights are provisioned through `POST /api/admin/rights` (platform administrator token required), which also records a `CONTENT_RIGHTS_GRANTED` audit event.
